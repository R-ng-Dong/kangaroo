# sdkconfig Reference — settings that are load-bearing

Some ESP-IDF settings look like tuning knobs but are load-bearing: change them and the device
still builds, still boots, and then fails days later under load or halfway through an OTA. This
file lists the ones we know are load-bearing, the value to use, and **what breaks if you change
it** — because a value with no reason attached gets "optimised" by the next person.

It is not a full sdkconfig dump. Anything not listed here we have no specific finding about.

## Who owns what

Both audiences own their own project's `sdkconfig`. `iotcore.a` ships pre-compiled, but
mbedTLS, the partition table, FreeRTOS and the WiFi stack are all compiled in **your** build, so
these settings are yours regardless.

| you set | app writer | SDK writer |
|---|:---:|:---:|
| mbedTLS, partitions, FreeRTOS / heap, WiFi buffers | ✅ | ✅ |
| `rogo_iot` options in `Kconfig.projbuild` (`CONFIG_IOT_IR_ENABLED`, `CONFIG_IOT_TCP_SERVER_ENABLED`, `CONFIG_IOT_MDNS_ENABLED`, `CONFIG_IOT_ETHERNET_ENABLED`) | ✅ | — |
| `iotPlatform` / `implplatform` `CONFIG_IOT_*` (you compile these) | — | ✅ |
| anything compiled into `iotcore.a` | ❌ | ❌ |

## Start here: symptom → setting

| what you actually see | almost certainly | do this |
|---|---|---|
| `Dynamic Impl: alloc(NNNN bytes) failed` → `esp-tls-mbedtls: write error :-0x7F00` → `MQTT_EVENT_DISCONNECTED`, under bursts of control commands | `MBEDTLS_SSL_OUT_CONTENT_LEN` too large | set it to **2048** |
| OTA download dies partway with a `-0x7100` read error | `MBEDTLS_SSL_IN_CONTENT_LEN` was reduced | restore **16384** |
| free heap looks healthy but TLS still fails to allocate | you are watching the wrong number | watch **largest free block**, not free heap |
| MQTT drops with `errno=0` / `errno=Success` and **no** alloc failure | not heap — the broker closed the connection | look at publish rate, not config |
| TLS fails with `-0x3B00` / `-0x2880` right after you enabled BLE 5.0 extended advertising | heap, not certificates — extended advertising costs ~9 KB | see *BLE 5.0 extended advertising* in the BLE Implementation Guide |
| NimBLE device boot-loops in `ble_gatts_start` once BLE Mesh is enabled | `CONFIG_BT_NIMBLE_DYNAMIC_SERVICE=y` | set it to **n** |

## The settings

### `CONFIG_MBEDTLS_SSL_IN_CONTENT_LEN` = 16384 — **never reduce**

The TLS receive record size. The OTA server sends records larger than 8 KB, so a smaller value
makes an OTA download fail partway through with `-0x7100`. The device builds, boots and runs
normally — it only breaks when you try to update it, which is the worst possible time to find
out.

Reducing this is a tempting way to reclaim RAM. Do not.

### `CONFIG_MBEDTLS_SSL_OUT_CONTENT_LEN` = **2048** (was 4096)

The TLS *send* record size — and the size of a contiguous block the device must allocate **on
every publish**.

With `MBEDTLS_DYNAMIC_BUFFER=y` (below), the TX buffer is freed between operations and
re-allocated per write. In ESP-IDF's
`components/mbedtls/port/dynamic/esp_mbedtls_dynamic_impl.c` the write path calls
`esp_mbedtls_add_tx_buffer(ssl, 0)` — passing zero — so `tx_buffer_len()` takes its `if (!len)`
branch and allocates the **full** size every time, regardless of payload:

```
OUT_CONTENT_LEN + 341   →   4096 + 341 = 4437 bytes, contiguous, per publish
```

A typical state report is **182 bytes**. At 4096 the device was reserving 4437 contiguous bytes
to send 182. When bursts of control commands briefly fragment the heap, that allocation fails
and the MQTT session drops.

At 2048 the demand is 2389 — measured on an ESP32-C3 with the same burst workload:

| | OUT=4096 | OUT=2048 |
|---|---|---|
| `alloc(...) failed` | 2 | **0** |
| `0x7f00` / esp-tls errors | 4 | **0** |
| MQTT disconnects | 2 | **0** |
| reports delivered | 184 | **241** |

Safe because TLS record size is transparent to the broker, and a payload larger than the record
size is fragmented across records by the protocol itself. Lower still (1024) is possible if you
need more margin; only go higher if you routinely publish multi-kilobyte payloads, and even then
fragmentation handles it.

**This reduces the probability of failure, not the possibility.** The new limit is a heap where
the largest free block falls below 2389.

### `CONFIG_MBEDTLS_DYNAMIC_BUFFER` = y — keep it on, know its cost

Frees TLS buffers between operations instead of holding them for the session's lifetime. On a
device with ~20 KB of free heap this is not optional: with it off, `IN_CONTENT_LEN` (16 KB) plus
`OUT_CONTENT_LEN` would be held permanently, which does not fit.

The cost is the per-write allocation described above — it converts "heap is briefly tight" into
"the MQTT connection dropped". That is the trade being made, and it is the right trade at this
RAM budget; the mitigation is keeping `OUT_CONTENT_LEN` small, not turning this off.

### `CONFIG_BT_NIMBLE_DYNAMIC_SERVICE` = **n**

The reference NimBLE driver registers GATT services statically, before the BLE host starts
(`IOT_BleStart()`), so dynamic services are not needed. Left on, they are dead weight — and
with BLE Mesh enabled they are a boot loop: mesh calls `ble_gatts_start()` itself, and with
dynamic services that second call re-initialises the service pool underneath entries already
allocated. If your board config sets it to `y`, turn it off; with mesh it is not optional.

### NTP servers — `CONFIG_IOT_NTP_SERVER_1..3`, `CONFIG_IOT_NTP_USE_DHCP_SERVER`

Optional; the platform builds with working defaults when you declare none of them. Keep an
IP literal in slot 1 and leave the DHCP option off unless your site actually serves NTP by
DHCP — a slow clock is a failed first TLS handshake, because the certificate cannot be
validated against a 1970 clock. Details and defaults: Platform Implementation Guide,
`IOT_TimerInit()`.

## Watch the right heap number

Free heap does not predict TLS failures. A device can have 12 KB free and still fail a 4437-byte
allocation, because what matters is the largest **contiguous** block:

```c
heap_caps_get_free_size(MALLOC_CAP_8BIT)             /* not the number that matters */
heap_caps_get_largest_free_block(MALLOC_CAP_8BIT)    /* this one */
```

Log the second before connecting and periodically under load. If it approaches
`OUT_CONTENT_LEN + 341`, you are close to the cliff.

Two things worth knowing so you read it correctly:

- **ESP-IDF's allocator (TLSF) coalesces on free**, immediately, with both neighbours. There is
  no accumulating fragmentation debt. A dip in largest-free-block reflects what is *live right
  now*, and it recovers when those allocations are released. A number that drops and stays down
  is a leak; a number that dips and returns is load.
- **Heap headroom varies a lot by chip.** An ESP32-C3 in this product family idles around
  `largest_block = 7680`; an ESP32-S3 around `49152`. A setting that is comfortable on one can
  be marginal on the other, so test on your tightest target.

## Not covered here

Deliberately left out rather than guessed at — we have no specific finding for these yet:
partition table sizing and OTA slot layout, FreeRTOS settings, WiFi buffer counts,
and power-management options. If you hit a problem traceable to one of those, tell us and it
belongs in this file. (The platform's own task stack sizes are source, not `sdkconfig`; see
*Task stacks* in the Platform Implementation Guide.)
